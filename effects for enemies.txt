========================================================

EFFECT SYSTEM ARCHITECTURE v2

========================================================

GOAL

--------------------------------------------------------

Create a generic effect system that:

works on enemies
works on players
works on props
works on future objects

without effect sources needing to know what they hit.

Examples:

Fireball → Knockback Effect

Ice Spell → Slow Effect

Gravity Spell → Pull Effect

========================================================

CORE PRINCIPLE

========================================================

Effects are DATA.

Actors own GAMEPLAY BEHAVIOR.

Processors manage EFFECT LIFECYCLE.

BAD:

Fireball → LaunchCharacter()

GOOD:

Fireball → Creates Knockback Effect → Target's EffectProcessor → Target Reacts

This keeps spells independent from targets.

========================================================

HIGH LEVEL FLOW

========================================================

Fireball Projectile

OnHit()

Create FEffectData + FEffectContext

Find Target's UEffectProcessorComponent

Processor Receives Effect

Processor Broadcasts Effect Event

Owner Reacts To Effect

Enemy launches itself

Rock applies impulse

Player gets slowed

========================================================

EFFECT TYPES

========================================================

Start simple:

enum class EEffectType : uint8

{

Knockback,

Launch,

Pull,

Slow,

Stun,

Root,

Burn,

Freeze,

StyleGain,

StyleLoss

};

NOTE:

This enum is fine for the first implementation.

If the game grows significantly, this can later evolve into a Gameplay Tag based system without changing the overall architecture.

========================================================

EFFECT DATA

========================================================

struct FEffectData

{

EEffectType Type;

float Magnitude = 0.f;

float Duration = 0.f;

FVector Direction = FVector::ZeroVector;

};

Purpose:

Magnitude = Strength of effect
Duration = 0 means instant effect
Direction = Used by knockback, pull, launch

========================================================

EFFECT CONTEXT

========================================================

struct FEffectContext

{

AActor* Source = nullptr;

AActor* Target = nullptr;

FVector ImpactLocation = FVector::ZeroVector;

};

Purpose:

kill attribution
style system
AI reactions
future damage system
combat logging

========================================================

ACTIVE EFFECT

========================================================

struct FActiveEffect

{

FEffectData Data;

FEffectContext Context;

float RemainingTime = 0.f;

};

Purpose:

Allows duration-based effects such as:

Slow
Burn
Stun
Freeze

Instant effects usually do not need to be stored.

========================================================

UEffectProcessorComponent

========================================================

IMPORTANT:

There is ONE EffectProcessorComponent PER ACTOR that can receive effects.

Example:

Player

└── EffectProcessorComponent

Goblin

└── EffectProcessorComponent

TrainingDummy

└── EffectProcessorComponent

Rock

└── EffectProcessorComponent

The processor is NOT a global singleton.

Responsibilities:

ReceiveEffect()
Store Active Effects
Tick Durations
Remove Expired Effects
Broadcast Effect Events

The processor does NOT decide gameplay behavior.

========================================================

OWNER REACTION

========================================================

The owner actor decides what an effect means.

Example:

Enemy receives Knockback

↓

Enemy launches itself using LaunchCharacter()

Rock receives Knockback

↓

Rock applies physics impulse to its mesh

Player receives Slow

↓

Player reduces movement speed multiplier

Each actor interprets the same effect differently.

========================================================

EXAMPLE IMPLEMENTATION

========================================================

Fireball OnHit():

1. Create EffectData

Type = Knockback

Magnitude = 1000.f

Direction = ForwardVector

Duration = 0.f

2. Create Context

Source = Fireball Owner

Target = Hit Actor

ImpactLocation = Hit Point

3. Find Processor

OtherActor->FindComponentByClass<UEffectProcessorComponent>()

4. Apply Effect

Processor->ReceiveEffect(Effect, Context)

5. Destroy Fireball

The fireball never needs to know if it hit:

Enemy
Boss
Player
Rock
Crate

========================================================

BASE CLASS DESIGN

========================================================

Recommended Unreal pattern:

AActor

└── ACharacter

└── ABaseCharacter

├── EffectProcessorComponent

├── HealthComponent (future)

└── AbilityComponent (future)

├── ABaseEnemy

├── APlayerCharacter

└── ABossCharacter

This is COMPOSITION, not inheritance-based effects.

The actor does not inherit from an "Effectable" class.

It simply owns an EffectProcessorComponent.

========================================================

INTERFACES

========================================================

Interfaces are still useful for capabilities such as:

LockOnTargetInterface
InteractableInterface
DamageableInterface (optional)

Shared implementation should usually live in a base class.

Example:

ABaseEnemy implements LockOnTargetInterface once.

All enemies inherit the implementation automatically.

========================================================

FIRST IMPLEMENTATION MILESTONE

========================================================

Implement ONLY:

EEffectType
FEffectData
FEffectContext
FActiveEffect
UEffectProcessorComponent
OnEffectReceived event
Knockback effect

Ignore for now:

Burn
Freeze
Slow
Stun
Stacking
Resistances
Immunities
Damage integration
Networking/Replication

Get Knockback working end-to-end first.

========================================================

DESIGN RULES

========================================================

1. Effects are data.
2. Spells create effects.
3. Actors own gameplay behavior.
4. EffectProcessor manages effect lifecycle.
5. Effects never know target classes.
6. Targets never know spell classes.
7. One processor exists per effect-receiving actor.
8. Shared functionality belongs in base classes.
9. Interfaces define capabilities, not shared data.
10. New effects should usually require only:
new effect type
new reaction code on relevant actors
optional processor logic for duration/stacking

========================================================

END

========================================================

This version reflects the key architectural improvement:

The effect system is now built around PER-ACTOR EffectProcessor components, while interfaces remain for capabilities such as lock-on rather than for storing effect functionality.

That's the part that changed the most from the original design and is the direction I'd recommend moving forward with.
